Abstract

TechFix is a newly established computer and mobile phone repair shop operating two branches in Sri Lanka, in Colombo and Galle. Because the business was recently founded, it lacked a technological platform to manage repair requests, branch operations, and customer communication. This project delivers TechFix Smart App, a native Android application that allows customers to register, browse repair services and spare parts, book repair appointments with photo evidence, track repair progress in real time, settle payments, and review their complete repair history — while staff manage appointments, technicians, spare-part inventory, service pricing, device showcases, payments, and customer accounts through a dedicated administrative workspace.

The application is built in Java with Material Design 3 components and follows an offline-first architecture: all data is persisted locally in a nine-table SQLite database accessed through hand-written DAO classes and a Content Provider, and synchronised bidirectionally with Google Firebase Firestore whenever connectivity is available. Advanced Android features integrated include GPS location services (nearest-branch detection using FusedLocationProviderClient and the Haversine formula), camera and image integration (device photos attached to bookings and staff-published repair showcases), complex data models with RecyclerView adapters (ListAdapter with DiffUtil), and simulated payment processing. The result is a robust, user-friendly dual-role application in which every functional objective of the brief is implemented and verified.

Introduction

Business Context

TechFix has rapidly become one of the popular repair service providers in Sri Lanka, yet its operations still rely on manual processes: walk-in dockets, paper-based part inventories, and no central record of customer repair history. As demand grows across its Colombo and Galle branches, this creates missed appointments, stock-outs of critical spare parts, unclear repair-status communication, and no mechanism for customers to discover services remotely.

Objectives

  • Maintain information about TechFix branches (Colombo and Galle), including locations and contact details.
  • Enable management of repair services, device categories, repair prices, spare-part availability, technicians, and sample images of repaired devices — and display this information to customers.
  • Allow customers to create accounts, log in, search available repair services, submit repair request appointments, and track repair status.
  • Assign repair requests to the nearest branch where technicians and required spare parts are available, supporting repair handling and payment processing.
  • Allow customers to view their previous repair history.
  • Additional objectives defined by the team: offline-first operation with cloud synchronisation, GPS-assisted branch selection, photo-based fault reporting, published repair showcases for customer trust, and an executive KPI dashboard for staff.

Scope of this Report

This report documents the requirement analysis, system design, development approach, advanced Android technologies used, results achieved, and a critical discussion of design decisions and limitations.

Architecture

The codebase is organised into clearly separated packages: activities (six screen hosts), fragments (five staff management tabs), adapters (eight RecyclerView adapters), database (SQLiteOpenHelper + DAOs + ContentProvider), models (twelve related entity classes), session (role-aware session manager), sync (FirebaseSyncManager singleton), and util (network monitoring, window-inset handling, analytics, nearest-branch calculator).

The application follows an offline-first, repository-mediated design: every user action writes first to SQLite; UI screens observe the local database; and a connectivity-aware synchronisation service mirrors changes to the cloud when online. This guarantees the app remains fully functional during network outages — essential for workshop environments with unreliable Wi-Fi.

Functional Modules

Customer journey. A guest lands on a public storefront showing the hero banner, five round category quick-filters (All, Phones, PC/Mac, Screens, Battery), the priced service catalogue, live spare-parts stock, and a horizontal showcase carousel of repaired devices. Registration/login supports both local SHA-256 credential verification and Firebase Authentication. The three-step booking form captures service, device category and model, problem description, optional camera/gallery photo, and preferred branch — validated against live spare-part stock at the chosen branch before submission, after which a technician with matching skill is auto-assigned. Customers track each docket through a live status timeline (Request Received → Repairing → Ready for Collection → Completed), pay outstanding invoices (cash at counter / card / bank-transfer simulation), and browse their complete Active/Completed repair history with filter chips.

Staff workspace. Five tabs: Overview (executive KPIs — active jobs, collected vs pending revenue, low-stock alerts, technicians on duty — plus walk-in docket creation and quick actions), Queue (searchable/sortable docket list with seven filter chips and one-tap stage updates), Inventory (part CRUD with ±stock adjusters and low-stock alerts), Catalog (service pricing CRUD per branch, technician roster with duty toggles and active-job load, showcase photo publishing), and Admin (customer directory with search, database diagnostics, forced cloud re-sync).

Smart assignment. Booking validates the required part is in stock at the selected branch and auto-assigns an available technician whose skill matches the device category (TechnicianDAO.availableFor()). GPS assistance uses FusedLocationProviderClient plus the Haversine formula to suggest and pre-select the nearest of the two branches; branch coordinates seed the database so the logic works fully offline.

Cloud sync engine. FirebaseSyncManager is a connectivity-aware singleton: it registers a ConnectivityManager NetworkCallback that triggers automatic push/pull whenever connectivity is restored, syncs immediately at startup when online, fires after every write operation, guards against concurrent runs, and notifies registered screens to refresh from local data once complete. Nine Firestore collections mirror the SQLite schema. An admin "Sync Now" control provides manual override.

Discussion

Key Design Decisions

Offline-first persistence. Workshops cannot rely on constant connectivity, so SQLite is the single source of truth and the cloud is a replica. This inverted the usual mobile pattern but eliminated every loading-failure state from the UX; the cost is a custom bidirectional merge in FirebaseSyncManager rather than relying on an online-only API.

Dual authentication backends. Local hashed credentials guarantee login works offline, while Firebase Auth adds industry-standard reset emails and prepares the app for future server-side features. Session state is role-aware, routing staff and customers to separate workspaces.

Constraint-driven data entry. Technician branch/skill and service categories are Spinner-bound to canonical values rather than free text, eliminating silent typos that previously could break skill-matched auto-assignment — a bug class discovered during internal testing.

Honest UI. Fabricated social-proof elements (hardcoded star ratings, blanket "Genuine OEM" claims) were deliberately removed in favour of verifiable information: real stock counts, warranty policy, tappable contact numbers, and authentic staff-published repair showcases.

Limitations and Future Work

  • Payments are simulated (ledger recording only); integrating PayHere/Stripe LKR checkout is the highest-value next step.
  • Branch selection suggests the nearest branch but final assignment honours the user's confirmed choice; a fully automatic routing mode using combined technician-and-stock availability queries is planned.
  • Date/time-slot selection for appointments (schema-ready time_slot column) is not yet exposed in the UI.
  • An embedded Google Maps SDK view would further enrich the branch page versus current external-map intents.

Challenges Encountered

Notable challenges included designing a conflict-safe two-way sync without a backend, keeping memory usage safe when displaying camera-captured bitmaps (solved via bounds-checked sampling), maintaining a consistent design language across 25+ screens (solved with shared style tokens and audits), and ensuring edge-to-edge insets behaved correctly across nested scroll containers.
